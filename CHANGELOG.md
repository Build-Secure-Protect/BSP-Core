All notable changes to BSP-Core. Format follows Keep a Changelog; versions follow SemVer.

## [Unreleased]

Nothing yet.

## [1.6.1] - 2026-10-26

### Fixed
- **Distant Horizons no longer takes a Velocity server switch for a Replay Mod recording.** On a switch, Forge Client Reset Packet (`clientresetpacket`) clears the client's level and then starts the next login with no server entry, so for the rest of the session the game said it was on no server; Distant Horizons read that as a replay ("Replay detected") and filed LODs under `Distant_Horizons_server_data/REPLAY`. A small client-only mixin (`bsp_core.mixins.json`, BSP-Core's first) reads the entry before the clear and hands it to the new login. It does nothing without Forge Client Reset Packet and is not loaded on servers. Checked in a dev client with Forge Client Reset Packet 0.3.1; the switch through Velocity is the owner's in-game test (`docs/TESTING.md`).

## [1.6.0] - 2026-10-26

### Added
- **`/bsp shop import <file> [test]`** (spawn shops request SS-1, part 1). Shops written as JSON (format 1, described in `docs/API.md`) in the server's `config/bsp_core/shops/` are checked in full first: any error (an unknown item or a mod the server lacks, unreadable NBT, a bad id, kind, style or currency, a missing parent or section, more than 21 cards on a page, a count above the stack size, a placeholder item, a coin sell price without `"allowCoinPayouts": true`, a rule that is not one, a rotation refill off a rotating shop) refuses the whole file and changes nothing. Otherwise every shop in the file replaces the shop of that id whole: posts, stalls and displays keep it; when its cards are the same items in the same places (only prices, notes or switches changed) its counts and draw stay, and only a card whose limits or rules changed starts its counts again; when cards changed, its counts and draw start again, here and on the network; the report says which. Shops not in the file stay. Warnings (a sell price at or above the buy price, above a third of it, the same item sold to a shop twice, a key this version does not know) are reported and the import goes ahead. Chat shows the summary and the first ten problems; the full report is `<file>-report.txt` beside the file. `test` does the checks and writes the report without changing anything. Refill and rotation rules may be written as objects (`{"after": 720}`, `{"every": "monday", "at": "00:00"}`) or as the short text the commands use. Admins and the console only. One game test; the spawn shops file reads cleanly (on a test server only its missing mods' items were refused).
- **`/bsp shop report [days] [shop]`** (spawn shops request SS-11). From the bank log's buy and sell rows: per shop, the pieces paid out to players for what they sold, the pieces they paid in, the net (out minus in: above 0, the shops made pieces) and the items moved, coins counted apart; the five busiest cards; the ten players who sold most; the total. Seven days by default, at most the log's `bank.logDays`. Every shop and item goes to `config/bsp_core/shops/report-<days>d-<date>.csv` for a spreadsheet. On a network it reads MySQL, so it covers every server. Admins and the console. Buy and sell rows now name the shop's id and the item's id (new `bank_log` columns `shop_id` and `item_id`, added to an existing table at start-up); rows from before count by the shop's name, as "(older rows)". The Sell Here box logs one row a card. One game test.
- **Search on the shop screen** (spawn shops request SS-9). A shop whose cards and sub-sections hold more than one page has a small search box at the right of its header (look B of `tools/preview/shop_search_concepts.html`); the page count sits beside it and goes while there is a search. From the second letter, the grid shows every card of the shop and its sub-sections whose name (as the player's game shows it, in their language) holds every word typed; a word starting with `@` matches the mod ("@create", "@create shaft"). Results go 21 to a page with Previous and Next; Escape empties the box. Hovering a result says which section it is in; clicking it opens that section on the page holding the card, which is picked out in amber for two seconds. A rotating section gives only its cards on show; cards hidden from the player by a requirement are not found, locked ones show with a padlock. The server sends the shop's tree once (a server cannot translate mod items' names) and opens only sections of the searched shop. One game test for the server side.
- **Cards and shops can need a rank or playtime** (spawn shops request SS-8). A card or a whole shop may need a permission node and hours of play, with an optional short reason. Locked and shown, a card is dimmed with what it needs in amber in place of its price ("Gold rank and up", "Rank", "10 h play") and a grey padlock in its corner; its tooltip says what it needs in red, the reason, and for playtime how far the player is ("Played: 4 h 12 m of 10 h"); it cannot be bought or sold to, and Sell all and the Sell Here box pass it by (look C of `tools/preview/locked_card_concepts.html`). Locked and hidden, a card is not on the player's page. A whole shop hidden from a player is left off their Shopping Network list and does not open for them ("This shop is not open to you."); shown, it opens with every card locked. Permissions are asked of LuckPerms through BSP-Core's bridge (Forge or Bukkit edition), so any node works, whenever it was typed; without LuckPerms only operators pass. Playtime is BSP-RankUp's count when it is installed (across the network when its storage is shared), otherwise this server's Time Played. Admins see locks as players do. Set with `/bsp shop item <id> <index> requires <spec>` and `/bsp shop set <id> requires <spec>` (`none`, or `permission <node>`, `playtime <hours>`, `show` or `hide`, `reason <text>`), or the import's `requires` key. One game test; LuckPerms and BSP-RankUp are untested (not on the test server).
- **`/bsp shop export <id|all> <file> [overwrite]`** (SS-1, part 2). Writes shops to `config/bsp_core/shops/<file>.json` in the import's format with every key (rules as objects, `allowCoinPayouts` when a card pays out coins), so a shop changed in the Workbench can be saved, edited and imported back. One shop comes with its sub-sections; `all` writes every shop. Counts and draws are not written. An existing file is kept unless `overwrite` is given. One game test: export, change, import back gives the same shops, key for key.
- **Sell limits on shop cards** (spawn shops request SS-2). A card can cap how many lots the shop buys back, from everyone and from each player. A sale that would pass the limit sells what is left and says so ("The shop takes no more of it for now; the rest is still in your inventory"); once it is used up the shop takes no more until it refills. Sell all and the Sell Here box stop at the limits and hand back the rest, and Max on the quantity screen counts the limit. Buying never gives back sell room, and selling never refills stock. Set with `/bsp shop item <id> <index> sell <global> <perPlayer>`. One game test for the limits, one for Sell all and Sell Here.
- **Refill rules for stock and sell limits** (SS-2, SS-4). Each count (stock for everyone, stock per player, sell room for everyone, sell room per player) refills by its own rule: `never`, a countdown from the moment it runs out (`90m`, `12h`, `2d`), every day at a time (`day 06:00`), every week on a day at a time (`monday 00:00`), or at each new draw of a rotating shop (`rotation`). A per-player rule may be `same`, following the shop-wide one (the default). Set with `/bsp shop item <id> <index> refill stock|stockplayer|sell|sellplayer <rule>` or on the Workbench's Limits tab. Fixed times use the new `shop.timeZone` setting (empty: the server machine's zone; set it the same on every server of a network). Counts refill when they are next read, so nothing has to tick.
- **Shop cards show what is left of a limit** in the top corner as "3/4": green for what you can still buy, amber for what the shop will still take from you (top left when a card has both), OUT or FULL in red at zero. A card goes dark only when it can neither be bought nor sold to. The tooltip says it in full ("You can sell 1 more of 4", "The shop takes 182 more from everyone", "Refills every Monday at 00:00 (in 2d 4h)"). Picked from `tools/preview/shop_limit_concepts.html`, look A.

- **The shop Workbench's side panel has two tabs, Card and Limits.** Card holds the lot size, prices, currency, instant, hidden and section. Limits holds a Buy group and a Sell group, each with everyone, each player, refill and player refill, and beside each shop-wide limit what is left of it now ("2 left"). Click a row and type in the field as before; while a refill rule is typed a tooltip lists the forms it may take; `none` (or -1) means no limit. A Refill now button fills every count on the card. Moderators see the tab and change nothing. Picked from `tools/preview/workbench_limits_concepts.html`, look A. One game test.

- **Shop counts are shared across the network** (spawn shops request SS-5, part 1). With `storage.mode = "mysql"`, every card's stock and sell room, for everyone and per player, lives in a new table `shop_counts`, the same on every server, for every shop. A trade first holds its lots in one locked database step (both counts at once), then takes the payment and hands over the items; a payment that fails gives the lots back. Two servers can no longer both sell the last lot, and a player's limit counts once across the network. Each server keeps a copy for its screens: a shop page reads its counts from the database when it opens, and open pages refresh when another server trades (Redis kind `shopcount`). If the database cannot be reached, a card with a limit refuses ("The shop's records cannot be reached right now; nothing was changed") and cards without limits trade as usual. At the first start with this version, the first server to start moves its saved counts to the database; the others' are dropped. Players' counts that are full again are swept away daily (lifetime limits stay). On a network the Sell Here box hands its items back to the inventory and sells each card's lots from there. One game test (with a stand-in for the database).

- **A rotating shop has one draw for the whole network** (SS-5, part 2). The draw lives in a new table `shop_draws`. When it is due, the first server to ask makes it under the database's lock and the others take it; the old draw shows on a server until the answer comes, and open screens refresh when it does (Redis kind `shopcount`). A server whose own draw predates this version offers it to the network at its first start with network storage, if the network has none yet (never later, so a draw for cards that have since moved cannot come back). A "refills each rotation" limit only ever refills forward, so a server not yet told of a new draw cannot refill it twice. One game test.

- **Rotating shops can change at a fixed time, without repeats, by weight, and say so** (spawn shops request SS-6). A rotating shop takes a change time (`monday 00:00`, `day 06:00`) in place of its interval; a draw from before waits for the next change time. With No repeats on, every card shows once before any shows again (when fewer are left than places on show, the rest come from a fresh cycle, never twice in one draw); cards moved, added or removed in the Workbench take their places in the draw and the cycle with them, so the same cards stay on show (a removed one leaves the draw one short until the next change). Each card has a weight from 0 to 100 (1 by default; 0 is never drawn). With Announce on, every player hears it when the cards change: "[Shops] Challenge now buys Steel Casing, Machine Frame, Brass Casing and Fluix Block. Next change Monday 00:00.", each card name showing the item when hovered (look A of `tools/preview/rotation_concepts.html`). Each server checks such shops every minute, so the change and the line come on time; on a network one server makes the draw and every server tells its own players once. The shop screen's "rotates in" counts to the change time. Set in the Workbench (below) or with `/bsp shop set <id> rotate <time|none>`, `/bsp shop set <id> norepeat|broadcast on|off` and `/bsp shop item <id> <index> weight <n>`. The network's draw keeps the cycle (`shop_draws.used`). One game test.
- **A card can buy back used items** (spawn shops request SS-7). A card set to match by item takes the same item whatever data it carries (a used machine with energy, upgrades or settings, a renamed tool), except the data that says what the item is: a potion's contents and an enchanted book's enchantments, so a water bottle is not a Potion of Strength. A damaged item is refused ("That one is damaged; this shop only takes it whole."), and so is one holding items, such as a filled shulker box, a backpack or a machine with items in its slots ("Empty it first: it holds items."). Where a shop has an exact card and an item card for the same item, the exact card wins its items; Sell all and the Sell Here box keep that order. The card's tooltip says "Takes any <item>, used or new (not damaged)". Set with the Workbench's Match line on the Card tab or `/bsp shop item <id> <index> match exact|item`. One game test.
- **A note on a card** (spawn shops request SS-10). Up to three lines of plain text, each up to 60 characters (longer ones are cut with "…"), shown at the foot of the card's tooltip on the shop screen after a blank line, in the Cash Machine's amber (look B of `tools/preview/card_note_concepts.html`). It is never put on the item a player gets. Set with the Workbench's Note line on the Card tab (lines with `|` between them; empty clears it) or `/bsp shop item <id> <index> note <line|line|line>` (`none` clears it). One game test.
- **The Workbench's Settings show only the lines for the shop's kind**, in one column with a thin rule between the groups (the shop; rotation or the special offer; opening hours): a rotating shop's slots shown, interval, rotate at, no repeats and announce; an offer's discount and end. The card's Card tab has a Weight line on a rotating shop. Look A of `tools/preview/rotation_concepts.html`.

### Changed
- **Moving, inserting or removing a card in the Workbench refills the counts of every card that changed place**, here and on the network (counts follow a card's place, so they would have landed on the wrong cards).
- **A refill rule of `rotation` is refused on a shop that does not rotate** ("Only a rotating shop refills each rotation"), in the Workbench and by command.
- **Per-player stock refills on its own** (SS-4). It used to come back only when the card's shop-wide stock ran out and restocked, so a per-player limit on a card without shop-wide stock lasted for ever. Cards saved before keep their meaning: their restock minutes become the rule for both stock counts, so a per-player limit with a restock now comes back that long after the player runs out; one without a restock is still a lifetime limit. One game test.
- **A rotating shop only buys what is on show** (SS-3). Sell, Sell all and the Sell Here box take a rotating shop's card only while it is in the current draw, as buying already did. Hidden cards of ordinary shops stay sellable. One game test.
- Editing a card in the Workbench, or `/bsp shop item ... stock|sell|refill`, fills every count on that card again (stock, sell room and every player's).
- A Market Stall's stock lamp and a Stall Display count a card the shop only buys as sold out once its shop-wide sell limit is used up.
- Built against BSP Region Guard 0.6.0 (its 0.5.0 jar is gone from its checkout). Region Guard stays optional at run time.

### Fixed
- The shop screen's "Bought ..." and "Sold ..." lines showed "Balance: %s pieces" with the number missing; they now show the balance.
- **A shop trade that finishes after the player has left takes and pays nothing** (shop code audit, item 1). On a network a trade waits a moment for the database; a player who logged out or changed server in that moment kept the items they were selling (their inventory was already saved) and was paid as well. Now a sale or buy that hears back after the player has left gives the held lots back and moves nothing, and Sell all stops there. A buy whose payment comes back after the player left keeps the items for them: they arrive at their next login, on any server.
- **A sale the bank does not credit gives the items back** (audit item 2). If the bank refused the credit (on a network, when the database fails at that moment), the items were already gone and nothing was paid. Now the items go back into the inventory, the sell room is given back, and the player reads "The bank did not take the sale; your items are back in your inventory." A card that pays 0 pieces now gives the items back the same way instead of keeping them.
- **A rotating shop's draw after an import, on a network** (audit item 4). Another server could hand the network its own old draw just after an import had emptied it, so the import's "the draw starts again" did not happen and the cards on show could be the wrong ones. Each network draw now names the shop record it was made for (new `shop_draws.for_shop`, added to an existing table at start-up): a server still holding an older record takes the network's draw but never makes one.
- **Moving, adding or removing a card in a rotating shop's Workbench** kept the draw's old places, so the shop showed and traded whatever card had moved into them (audit item 5). The draw and the no-repeat cycle now follow the cards.
- **Draws on a network read a copy of the shop** made on the server thread, not the record the Workbench may be changing at that moment, which could make an empty draw or an error (audit item 10).
- **A rotating shop with nothing to draw** (every card hidden or at weight 0) made a new empty draw at every look, and on a network asked the database each time; it now waits for its change time like any draw, and draws at once when a card can be drawn again (audit item 11).
- **The server that ran an import announces the replaced shop's new draw** like the others (audit item 23).
- **A shop whose parents go round in a loop froze the server** when opened (audit item 6). The Workbench's Parent row and the import now refuse a parent that would put a shop under itself, or more than 16 deep ("That parent would put the shop under itself (or more than 16 deep)."), and every walk up the shop tree stops after 16 steps anyway.
- **A shop's requirement now covers everything under it** (audit item 7, owner's pick a). A sub-section, and a sub-section of that, is locked or hidden whenever a shop above it is; the section card that opens a locked or hidden shop is locked or hidden with it, and pressing a locked one opens nothing ("That is locked for you"). Before, a locked shop's section cards still opened, and players could buy in the sub-section; search found the cards of a hidden section's own sub-sections.
- **A rotating shop whose cards refill each rotation cannot be changed to another kind** in the Workbench ("A card here refills each rotation: change that refill rule on its Limits tab first."); those counts would never have refilled again (audit item 16).
- **Cards and shops a requirement hides stay off stall counters and Stall Displays**, which everyone passing sees, and do not count as the venue's stock (audit item 17).
- **The Workbench's TEST key opens a shop hidden by a requirement**, for an admin without the node too, with the hidden cards shown locked; sections and Back keep TEST mode (audit item 21).
- **Two servers trading the same card at the same moment could deadlock in MySQL** (audit item 8), and one player then read "The shop's records cannot be reached". The rows of a card side, and a rotating shop's draw, are now locked exclusively from the first statement, a transaction MySQL ends over a lock is tried once more, and a server waits at most 5 seconds for another's lock, so a slow lock cannot hold up its other database work.
- **A trade no longer makes every other server re-read the whole shop** (audit item 9). The notice after a trade names the card side and the player, and the other servers read just those two rows; the whole shop is read only after a reset, a move, an import or a new draw, and then the draw is read without a lock. Only the server that made a new draw tells the others.
- **Shop pages cost less to send** (audit item 12). A card is found by its place without copying the shop's list (it was copied at every look-up, inside loops: Sell all on a 200-card shop made over a million card checks); a page asks the shop's own requirement once instead of once a card; BSP-RankUp's playtime and LuckPerms on Mohist look up their methods once; whether a shop shows the search box is worked out once and again only when a shop changes.
- **The shop search asks for a fresh list each time the shop is opened**, so it never shows yesterday's draw, prices or locks; a click on a result that has gone says "That card is not there any more; search again." instead of doing nothing; the results are worked out once per query, not several times a frame (audit item 18).
- **A click on a search result is checked against that shop and card alone** (under the searched shop, not hidden, on show), not by building the whole tree again (audit item 19).
- **Editing a card's price, note or switches no longer refills its limits** (audit item 13, owner's pick a). Only a change to a limit, a refill rule, the lot size or the match rule starts a card's counts again, the same in the Workbench and by command (`match` by command now does too). Fixing a note in the middle of the week no longer lets everyone sell the Challenge's weekly cap twice.
- **Re-importing a shop with the same cards keeps its counts and draw** (audit item 14, owner's pick a; this changes what the import did before). A price fix in the Challenge file no longer rerolls the week's cards or refills the sell limits; its change time keeps its date. The import report and chat say which shops kept theirs.
- **Text that would not fit is refused** (audit item 15): a shop name over 64 characters (import, Workbench, cut in `/bsp shop create`), a requirement's reason over 64 or permission over 128 (import, `requires` command). Before, such a reason stopped the shop screen opening, and such a name kept the shop off the other servers. Long section paths are shortened with "…".
- **The import reports odd files instead of failing** (audit item 20): a text `format`, a non-boolean `allowCoinPayouts` or an id that is not text is an error line; a section card's prices and limits (ignored) are a warning; `style`, `match` and `whenLocked` are read in any case.
- **The shop report** says the database is out of reach instead of reporting this server alone when network storage is wanted but not connected; on a server alone it says each player's log keeps only its newest rows; `bank_log` gains an index for the report's query (audit item 22).
- **A Workbench lot is never more than a stack of the item** (audit item 24): 64 ender pearls become 16, a sword card holds one sword. Such a card could never be bought, and the export wrote a count the import refused.
- Seven lang lines nothing used any more are gone (audit item 25).
- **The Sell Here box keeps its items when its player logs out** (audit item 3). Minecraft saves a leaving player before it closes their screen, so whatever the box handed back at logout was never saved. The box is now settled when the player logs out, before the save: on a server alone it sells as closing would; on a network it hands everything back unsold. The box no longer takes a Shatter Totem.

## [1.5.0] - 2026-10-25

### Added
- **Herald, a new totem upgrade** (the first part of the Discord steal warnings). A one-level Base power on the Walls path, after Alarm at tier II, priced like Sentinel (Raid prices); its node reads HR. It is locked, with "This server is not linked to Discord", unless the server's new `discord.enabled` is on, and always in a single-player or LAN world. It sends nothing by itself: the Discord bot reads the alerts below. One game test.
- **Discord steal alerts go out over Redis for the bot** (the second part). When the game warns an owner that their totem is being stolen (after the thief's Shroud), the totem's server publishes a public line for the alert channel ("a totem is being stolen on <server>", nothing more) and, when the totem has Herald, a message for the owner with the server, place, thief and time left; when the steal ends, the owner who was told gets the outcome (stolen, or saved and why). One of each per steal, and at most one warning per player every 30 seconds. New settings `discord.serverName` and `discord.redisChannel` (default `bsp_core:discord`); the format is in `docs/API.md`. Nothing reaches Discord until the bot (BSP-Velocity Additions) reads the channel. Two game tests.
- **Linking a Discord account** (the third part). `/bsp discord link` (or LINK on Herald's card) gives a six-character code for ten minutes; the player types `/link CODE` in the BSP Discord, where the bot learns who they are from Discord itself. The player never types a Discord name, id or password in the game, and the game never holds one. A new code replaces the last; five an hour. `/bsp discord status` says linked, not linked or the waiting code; `/bsp discord unlink` ends the link and tells the bot to forget it. Herald's card shows the player's own line under Buy: "Discord: not linked" with LINK, the code with its minutes and where to type it, or "Discord: linked ✓" with UNLINK. Codes and the linked flag live on Redis under `discord.redisChannel` (see `docs/API.md`). Two game tests.
- **A player whose Discord message could not be delivered is told at their next login** (DMs closed, or not in the BSP Discord any more): one line, "Your Discord warning could not reach you: allow DMs from the BSP server", and nothing public. The bot leaves the note on Redis (`<channel>:undelivered:<uuid>`); the game takes it at login so the line shows once. One game test.
- **The guide book covers Herald**: a line in the Base walls list, and two pages in Powers in Detail ("Herald" and "Linking Discord"). Setting up the game servers is in `docs/DISCORD_SETUP.md`.

### Changed
- **An owner on another server no longer gets a clickable "recall to it" chat line** when their totem is being stolen. That line ran `/bsp recall <server>`, a staff-only command, so it failed for players. They still get the steal warning wherever they are; the Recall popup is for an owner on the totem's own server. One game test.
- `/bsp` is open to every player so they reach `/bsp discord`; every other `/bsp` command keeps the operator-or-moderator rule it had (a game test checks a plain player can use `discord` and nothing else).

### Fixed
- **Harvest, Sentinel, Extra Homes, Swift Travel and Herald have their own orb colours** round a placed totem (yellow-green, violet, sea green, amber and rose). They all drew plain red, the same as Lockpick, because the colour list stopped at the first 26 upgrades. One game test checks every upgrade has a colour of its own.
- A projector base or battery charger saved before an upgrade was added no longer forgets which plasma powers it offers until its next refresh.

## [1.4.6] - 2026-10-25

### Fixed
- **BSP-InventorySync's placeholders are refused wherever an item would be lost or copied** (BSP-InventorySync request R6). An item whose mod a server lacks travels as a placeholder holding the original; sold, the original was gone for good, and made into a shop card, a kit or a season prize it would hand copies of the original to everyone. A shop card cannot be made from one (`/bsp shop add` and the shop workbench), a shop whose card is one neither sells nor buys it (sell-all and the Sell Here box hand placeholders back), a kit holding one is not saved, and a season prize slot does not take one; each refusal says it is a placeholder for a missing mod's item. Storage (the safety deposit box, vaults) keeps placeholders as they are. One game test.
- **A single-player or LAN world never joins the network's database** (BSP-InventorySync request R7). The client pack ships the servers' configs as defaults, so a new single-player world started with `storage.mode = "mysql"` and a server's `storage.serverId`, and joined the network's MySQL and Redis as that server: bank changes, placed totems, first-join grants, kits redeemed and owed items collected in that world landed on the real network. The server built into a game client now keeps every record in the world save whatever the storage settings say, writes one line to the log saying so, and refuses `/bsp storage test` and `/bsp storage migrate`; `/bsp storage` says why storage is off. The no-totem server list is ignored there too, so a test world named after a no-totem server still allows placement. Dedicated servers (and the GameTest server) are unchanged. One game test.

## [1.4.5] - 2026-10-23

### Added
- **The MySQL driver through the api** (BSP-Teleport request R9). `BspStorage.jdbcDriver()` hands out a new instance of the JDBC driver BSP-Core itself uses (the one bundled, relocated, in the full jar; the server's own MySQL driver with the slim jar; else MariaDB's), `jdbcDriverClass()` its class name and `jdbcUrlPrefix()` the URL scheme it takes. Other mods no longer need the hidden relocated class name. One game test.
- **The leaderboard through the api** (BSP-RankUp request RU-R1). `BspScores.score(server, uuid)` (rank, points, totems held, best tier), `points`, `totemsHeld`, `bestTier` (1 for Tier I to 5 for Tier V, 0 for none) and `board(server)`, read from the last board (every server's combined on a network). A `ScoreEvent.Changed` is posted on the server thread whenever a rebuilt board gives a player different points (with the difference); none for the first board after a start. One game test.
- **`/bsp totem forget <player>` and `BspTotems.forgetPlayer(server, uuid)`** (BSP-Stress Test request ST-C1): the totem wipe without the fresh totem, for an online or an offline player (named by profile, so a bot that has left can be cleaned). - Guardian artwork: a kneeling creeper-man statue holding an ender-pearl orb, as a 3D block model used by both the item and the block. Item pulses turquoise to blue. Block body is gold when owned, turquoise when unclaimed, flashing gold and red while being stolen (`glow` block state). Upgrade levels show as small tinted orbs around the base (`damage`, `resistance`, `mining_speed` block states, 0 to 5), pale at level 1 and vivid at level 5. Assets are generated by `tools/gen_totem_concepts.py assets guardian`.
- Operator column in the totem panel (permission level 2): assign an owner by name (online, cached, or any name for testing), unclaim, cancel or finish the current steal, view and adjust each buff level, reset buffs. Lets one operator test the full steal flow alone.
- Unclaimed placed totems must be stolen like any other, but only take `steal.unclaimedStealSeconds` (60) to claim. Nobody but an operator can mine an unclaimed totem.
- Stealing: right-click a placed totem to open its panel. Non-owners get a **Steal** button. The thief must stay within `steal.radiusBlocks` (5) for `steal.stealSeconds` (300); leaving the radius starts a `steal.graceSeconds` (15) countdown after which the attempt fails. Dying or logging out fails it. One thief at a time. Success transfers ownership. Thief and owner both get a HUD countdown and chat messages.
- Upgrade tree: right-click with the totem in the main hand (sneak + right-click a block to place it instead). Damage, Resistance and Mining Speed buffs with five levels each, bought with XP levels from the `upgrades` config. Upgrades are stored on the totem and survive placing, picking up and stealing. Buffs apply while the totem is in the offhand: +1 attack damage per level, Resistance effect at level-1 amplifier, +25% mining speed per level.
- Operator commands: `/bsp totem give <player>`, `/bsp totem reset <player>`, `/bsp totem locate <player>`, `/bsp totem owner`.
- Dropped totems use their own entity: never despawn, immune to all damage, fire and explosions, return from the void, and place themselves as a block after `restrictions.groundSecondsBeforePlace` seconds (default 30). Only the owner can pick one up.
- Only the owner (or an operator) can mine a placed totem.
- The totem can only be placed or dropped in `restrictions.allowedDimensions` (Overworld, Nether, End). Elsewhere it snaps back into the inventory.
- Totems are pulled back out of any container that is not the player's own inventory.
- On death: killed by a player places every carried totem next to the body immediately; any other death drops them as the 30 second ground item. Deaths outside an allowed dimension send the totem to the player's last position in one. Grave mods never see the totem.
- First-join grant: a server with `first_join.grantTotemOnFirstJoin = true` gives each new player one owned Shatter Totem, recorded in both the player's persistent data and a world-level ledger (`data/bsp_core_totems.dat`) so it can never be granted twice.
- Config section `upgrades` with editable XP level costs for the Damage, Resistance and Mining Speed buffs (defaults 5/10/20/35/55).
- Shatter Totem block, block entity and item (`bsp_core:shatter_totem`): one per stack, fire resistant, epic rarity, glint, cannot be damaged as a dropped item, cannot enter shulker boxes or bundles. Block is immune to explosions, pistons and non-player entities, emits light, and returns the exact totem (owner intact) when mined.
- Totem ownership stored in item NBT and the block entity; shown in the tooltip and on right-click.
- "BSP" creative tab.
- Placeholder textures generated by `tools/gen_textures.py` (no dependencies).
- Project skeleton from the Forge 1.20.1 MDK (Forge 47.4.10).
- Server config with `grantTotemOnFirstJoin` (default off).
